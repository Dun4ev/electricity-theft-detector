# Архитектура MVP: Система выявления краж электроэнергии

Документ описывает архитектуру, аппаратный состав, программно-алгоритмический стек и пошаговый план создания минимально жизнеспособного продукта (MVP) для контроля баланса электроэнергии и обнаружения несанкционированных подключений.

---

## 1. Схема архитектуры системы (Физический и Логический уровни)

Ниже представлена схема прохождения энергии и данных от физического оборудования до аналитического модуля и интерфейса оператора.

```mermaid
graph TD
    subgraph Physical_Grid ["Физическая электросеть"]
        Sub["'ТП / Трансформатор (Источник)'"] --> F1["'Фидер 1 (Линия)'"]
        F1 --> C1["'Потребитель 1 (Умный счетчик)'"]
        F1 --> C2["'Потребитель 2 (Умный счетчик)'"]
        F1 -.->|"'Кража / Наброс на линию'"| Theft["'Нелегальный потребитель'""]
    end

    subgraph Data_Acquisition ["Сбор и передача данных (AMI)"]
        BM["'Балансовый счетчик (ТП)'"] -.->|"'RS-485 / Modbus / GSM'"| Gateway["'Шлюз сбора данных (Концентратор)'"]
        C1 -.->|"'RF / LoRaWAN / GSM'"| Gateway
        C2 -.->|"'RF / LoRaWAN / GSM'"| Gateway
    end

    subgraph Storage_And_Analytics ["Хранение и Аналитика"]
        Gateway --> MQTT["'Брокер сообщений (MQTT / Kafka)'"]
        MQTT --> TSDB[("'База данных временных рядов (TimescaleDB / InfluxDB)'")]
        TSDB --> Alg["'Аналитическое ядро (Python / ML)'"]
    end

    subgraph Presentation ["Интерфейс"]
        Alg --> UI["'Дашборд оператора (Streamlit / Grafana)'"]
        Alg --> Alert["'Система алармов (Telegram / Email)'"]
    end

    %% Связи физического контроля
    Sub -.->|"'Измерение отпуска'"| BM
```

## 2. Предложения по оборудованию (Аппаратный уровень MVP)

Для запуска MVP важно использовать доступное и легко интегрируемое оборудование. Рассматриваем два сценария: **промышленный (пилотный)** и **лабораторный (настольный)**.

### Вариант А: Промышленный пилотный стенд (для реального СНТ / поселка)

| Узел | Оборудование | Описание / Интерфейсы |
| :--- | :--- | :--- |
| **Балансовый счетчик (ТП)** | **Меркурий 234 / 236** (трехфазный) | Устанавливается в шкафу ТП. Поддерживает интерфейс RS-485 или GSM-модем. Измеряет профиль мощности, токи и напряжения по фазам. |
| **Счетчики потребителей** | **Меркурий 206 / Миртек-12-РУ** | Однофазные умные счетчики со встроенным радиомодемом (RF 433/868 МГц) или PLC/LoRaWAN. |
| **УСПД (Концентратор данных)** | **УСПД Меркурий 250** или контроллер **Wiren Board 7** | Собирает данные со всех счетчиков по радиоканалу/RS-485 и отправляет их на сервер по GSM/Ethernet. |

### Вариант Б: Лабораторный прототип (для тестирования "на столе")

> [!TIP]
> Идеально для быстрой и дешевой проверки гипотез перед покупкой промышленного оборудования.

*   **Контроллер**: ESP32 или Raspberry Pi.
*   **Датчики тока**: Неинвазивные трансформаторы тока **SCT-013** (надеваются на провод без разрыва цепи).
*   **Датчики напряжения**: Модули **ZMPT101B** (для измерения переменного напряжения).
*   **Нагрузка**: Обычные бытовые приборы (лампа, чайник) для имитации честных пользователей и "вора".

## 3. Программно-алгоритмический стек для MVP

Для MVP выбираем стек с минимальным временем разработки и высокой скоростью обработки временных рядов.

### Инфраструктурный стек
*   **Сбор данных**: **Eclipse Mosquitto** (MQTT-брокер). Легкий протокол передачи данных от счетчиков/УСПД.
*   **База данных (БД)**: **PostgreSQL + TimescaleDB**. Позволяет хранить данные как временные ряды (быстрые агрегации по времени) и одновременно вести классические реляционные таблицы (реестр абонентов, топология сети).
*   **Backend**: **Python (FastAPI)**. Быстрый и простой API для передачи данных в дашборд.
*   **Визуализация (Дашборд)**: **Grafana** (готовые графики баланса за 10 минут) или **Streamlit** (для кастомного интерфейса на чистом Python).

### Алгоритмический стек (Python)
Поскольку на старте MVP размеченных исторических данных о кражах (классифицированных датасетов) не будет, классическое обучение с учителем (Supervised Learning) неприменимо.

```
                  ┌──────────────────────────────┐
                  │   Сбор данных со счетчиков   │
                  └──────────────┬───────────────┘
                                 │
                  ┌──────────────▼───────────────┐
                  │    Расчет баланса на ТП      │
                  │   (Выявление факта кражи)    │
                  └──────────────┬───────────────┘
                                 │
                  ┌──────────────▼───────────────┐
                  │ Анализ аномалий потребителей │
                  │  (Локализация: кто именно)   │
                  └──────────────┬───────────────┘
                                 │
            ┌────────────────────┴────────────────────┐
            ▼                                         ▼
 ┌─────────────────────┐                   ┌─────────────────────┐
 │  Статистический     │                   │  Машинное обучение  │
 │  метод (Z-Score)    │                   │ (Isolation Forest)  │
 └─────────────────────┘                   └─────────────────────┘
```

1.  **Расчет энергобаланса (Физический уровень)**:
    *   **Библиотеки**: `Pandas`, `NumPy`.
    *   **Суть**: Почасовое сопоставление отпуска с ТП и суммы потребления абонентов с учетом поправки на технические потери (обычно 4-8% в зависимости от длины линий).
2.  **Выявление аномальных потребителей (Локализация)**:
    *   **Метод 1: Статистический (Z-Score / СКО)**:
        Анализ резких отклонений текущего потребления абонента от его исторического среднего профиля (например, потребление упало на 80%, хотя хозяева дома).
    *   **Метод 2: Обучение без учителя (Anomaly Detection / unsupervised)**:
        *   **Алгоритм**: **Isolation Forest** (из библиотеки `scikit-learn`). Отлично изолирует аномальные профили нагрузки.
        *   **Алгоритм**: **DBSCAN** или **K-Means** (кластеризация). Позволяет сгруппировать абонентов со схожим поведением и выделить тех, кто резко выбивается из группы (например, все соседи зимой греются электричеством, а у одного потребление нулевое).

## 4. Пошаговый план реализации минимального MVP

> [!IMPORTANT]
> Главная цель MVP — подтвердить, что система способна свести баланс по времени и указать на аномального потребителя, используя реальные или синтетические данные.

### Шаг 1: Генератор синтетических данных (Неделя 1)
Если физического оборудования еще нет, пишется Python-скрипт, который генерирует:
*   Нормальные профили потребления 10 абонентов (с шумом, дневными/вечерними пиками).
*   Профиль 1 абонента-"вора" (у которого в определенный день потребление падает на 70%).
*   Профиль балансового счетчика ТП (сумма всех 10 абонентов + технические потери + скрытое потребление вора).

### Шаг 2: Развертывание БД и Сборщик данных (Неделя 1)
*   Запуск PostgreSQL с расширением TimescaleDB в Docker.
*   Создание таблицы `meter_readings` (id_счетчика, timestamp, active_power, voltage).
*   Скрипт-загрузчик импортирует данные в БД.

### Шаг 3: Разработка аналитического скрипта (Неделя 2)
*   Написание SQL-запросов для быстрого сведения баланса: группировка данных по 30-минутным интервалам и вычисление разницы.
*   Написание Python-функции (Isolation Forest), которая на входе принимает матрицу профилей потребления абонентов за последние 14 дней, а на выходе выдает `Anomaly Score` для каждого абонента.

### Шаг 4: Интерфейс оператора (Неделя 2)
*   Развертывание Streamlit-приложения.
*   **Экран 1**: График общего баланса ТП (красная зона — когда разница между отпуском и потреблением превышает норму).
*   **Экран 2**: Рейтинг подозреваемых абонентов с наибольшим `Anomaly Score` и кнопка "Посмотреть профиль нагрузки" для ручной верификации.
